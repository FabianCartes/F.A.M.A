**Estado: conexión directa aplicada, comprobada por el padre y verificada independientemente; sincronización en cola no habilitada.** Solicitud de planificación: «Prepara el plan para esta salida simple, verifica que no cause errores en el entorno». ### Alcance y cambio mínimo

Conservar la red interna actual de API/PostgreSQL y la IP172.23.0.3 que utiliza el frontend. Añadir a la API una segunda red bridge dedicada, con salida a Internet y sin publicar puertos; PostgreSQL no se conecta a esa red. No cambiar la red interna ni su indicador internal. No desplegar el proxy candidato, ni instalar dependencias ni construir otra imagen para este cambio de configuración.

La API necesita una recreación controlada para añadir las variables GCS y el montaje de credenciales: mismo ID de imagen, usuario1000:1000, raíz de solo lectura, privilegios/capabilities, límites, GPU, caché offline, volúmenes y parámetros de ejecución originales. Montar una copia privada de la credencial existente como solo lectura en /run/secrets/gcs-service-account.json, legible solo por su propietario; configurar GCS_BUCKET_NAME, GOOGLE_APPLICATION_CREDENTIALS y GCP_KEY_PATH. No imprimir secretos ni introducirlos en Git. No habilitar startup normal: isolated evita el worker automático de feedback y el seeding. Mantener frontend dev, PostgreSQL local y worker ZIP sin cambios.

La salida general es un cambio explícito de seguridad: no limita destinos a Google. Sin publicar puertos adicionales no se habilita una nueva entrada desde el host, pero la API tendrá capacidad de iniciar conexiones externas. La clave existente ya acredita lectura, no permisos mínimos ni escritura. El montaje de solo lectura no restringe los permisos IAM de esa identidad.

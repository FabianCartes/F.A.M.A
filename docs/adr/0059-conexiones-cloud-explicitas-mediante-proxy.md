# Conexiones Cloud SQL explícitas mediante proxy externo

El nodo institucional usa PostgreSQL en Cloud SQL y objetos en GCS, mientras el desarrollo conserva PostgreSQL local. Se mantiene SQLAlchemy y el controlador PostgreSQL existentes, con Cloud SQL Auth Proxy como proceso externo. Así se puede comprobar el mismo transporte desde Windows y Docker sin incorporar otro controlador de base de datos ni implementar la renovación de certificados en la aplicación. El coste es operar y actualizar también el proxy; este no sustituye los permisos SQL ni proporciona una ruta hacia una VPC privada.

La selección de nube es explícita. El arranque nativo toma un registro elegido por el operador y reemplaza las variables de conexión anteriores; la variante Compose sustituye las dependencias y el entorno locales, usa la red interna del proxy y exige identificar la instancia. Una caída no selecciona otra base. Las vistas nativa y Docker preparadas para pruebas contienen referencias distintas al mismo conjunto de secretos; son alternativas de ejecución y ninguna queda finalizada automáticamente. Windows protege el directorio mediante una DACL para el usuario actual y SYSTEM; POSIX utiliza permisos privados. La contraseña del migrador no forma parte de la configuración diaria.

El diagnóstico realiza una consulta SQL de solo lectura y un listado GCS por separado, con resultados sanitizados. Acredita conectividad y permiso de listado, sin afirmar compatibilidad del esquema ni permiso de escritura. Las migraciones y el estado de instalación siguen el [ADR 0040](0058-configuracion-persistente-y-migraciones-explicitas.md); el asistente y su finalización siguen pendientes. El [manual de conexiones](../manuales/conexiones_cloud_sql_y_gcs.md) documenta la operación y el alcance observado de las pruebas.
